신청서 §3.3 "본 과제의 핵심". 이 저장소의 로컬 파싱 작업(1~9단계)과 분리된 작업줄기라 **별도 세션에서 수행**한다.

## 1. 시나리오 매트릭스 — 4개 전부

**전제: 탈옥/루팅 없는 일반 단말.** 취득 경로는 전부 비침습(non-invasive) 수단만 쓴다.

| # | 단말 | 에이전트 | 폰 측 취득 방법(1순위) | 대체 경로 |
|---|---|---|---|---|
| S1 | iOS | Claude Code | 암호화 백업(Finder/idevicebackup2) → `Manifest.db` 앱 도메인 | Safari `History.db`·스크린 레코딩 |
| S2 | iOS | Codex | 동일 | 동일 |
| S3 | Android | Claude Code | `adb bugreport` + `logcat` + `/sdcard/Android/data/<pkg>` | `adb backup`(allowBackup 확인 후)·스크린 레코딩 |

### 호스트 환경 제약 (중요)

WSL2에는 **USB 패스스루가 없다.** `usbipd` 로 attach하지 않는 한 WSL의 `adb`·`idevice*` 는 단말을 보지 못한다.
→ 두 단말 모두 **Windows 측 도구로 취득하고, 산출물을 `/mnt/c/...` 경유로 WSL에서 파싱**한다. usbipd attach는 iTunes 백업 경로를 깨뜨리므로 쓰지 않는다.

```bash
ADB=/mnt/c/tools/platform-tools/adb.exe   # WSL에서 이 경로로 호출
$ADB devices -l
```

### 착수 전 리스크 2건

**1. iOS 26.5 × iTunes for Windows 12.13.10.3 — 백업 호환성 미검증 (최우선 확인)**

iOS 26은 2025년 이후 릴리스이고 Apple은 Windows용 iTunes를 `Apple Devices` 앱으로 대체했다. 현재 설치된 iTunes 12.13.10.3 이 iOS 26.5 백업을 정상 처리하는지 **다른 무엇보다 먼저 확인**한다. 실패 시 폴백 순서:

| 순위 | 수단 | 비고 |
|---|---|---|
| 1 | iTunes 12.13.10.3 "이 컴퓨터에 백업" + **로컬 백업 암호화 체크** | 성공하면 `Info.plist`·`Manifest.db` 즉시 확보 |
| 2 | Microsoft Store `Apple Devices` 앱 | iTunes 후속. 백업 포맷 동일 |
| 3 | 3uTools `Backup/Restore` | 이미 설치됨. 표준 iTunes 백업 포맷 생성. 암호화 옵션 확인할 것 |
| 4 | `usbipd attach` → WSL `idevicebackup2 backup --full` | **최후 수단** — attach 중에는 Windows 측 iTunes/3uTools가 단말을 못 본다 |

**암호화는 반드시 켠다.** 키체인 항목은 암호화 백업에만 들어간다. 백업 암호는 별도 안전한 곳에 기록하고 문서에는 남기지 않는다.

**2. 양 단말 모두 에이전트 앱 미설치** — Android `pm list packages | grep -iE 'anthropic|claude|openai|chatgpt'` → 0건. iPhone 도 3uTools `Apps` 탭 기준 사용자 앱 1개뿐.
→ 오히려 유리하다. **설치 전 스냅샷 → 앱 설치 → 설치 후 스냅샷** 순서로 가면 "앱이 처음 만드는 파일 집합"이 공짜로 나오고, 이후 원격제어 세션 차분에서 노이즈가 거의 없다. 이 3단 스냅샷을 실험 절차(§3)의 0단계로 넣는다.

## 3. 통제 실험 절차 (시나리오별 반복)

원본 무변경. 취득 도구는 `scripts/remote-snapshot.py` (read-only, 파일별 size·mtime·SHA-256).

```bash
# 1) 사전 스냅샷
python3 scripts/remote-snapshot.py snap S1-before artifacts/remote

# 2) 원격제어 세션 1회 실행
#    - 로컬에서 원격제어 활성화
#    - 폰 앱에서 명령 1건 지시 (권장: 특정 표식 파일 읽기 — 예: /tmp/AGENTRACE-MARKER.txt)
#    - 지시 시각·문구를 사람이 별도 기록 (폰 화면 캡처 = 대조 기준점)

# 3) 사후 스냅샷 + 차분
python3 scripts/remote-snapshot.py snap S1-after artifacts/remote
python3 scripts/remote-snapshot.py diff artifacts/remote/snap-S1-before.json artifacts/remote/snap-S1-after.json
```

표식 파일을 쓰는 이유: 로컬 이벤트 수만 개 중에서 **이 원격 지시로 발생한 행위를 유일하게 특정**하기 위함.

차분 후 확인 항목:
1. `~/.claude.json` 원격 관련 키 변화
2. `state_5.sqlite` `remote_control_enrollments` 신규 row (websocket 엔드포인트·server_name·account 식별자)
3. 세션 JSONL에 **원격 여부를 구분하는 필드**가 있는가 (없으면 "로컬 기록만으로는 원격/로컬 구분 불가"가 그 자체로 발견)
4. 신규 디렉터리·토큰·캐시 (Codex `.tmp`, Claude `.claude/` 하위)
5. 우리 도구로 파싱했을 때 그 행위가 Event로 잡히는지, actor가 무엇으로 판정되는지

## 4. 폰 측 취득 — Android 루팅 / iOS 비탈옥

**비대칭 전제**: Android는 Magisk 루팅 단말이라 내부 저장소를 직접 뜬다. iOS는 비탈옥이라 백업 경로만 쓴다.
이 비대칭 자체가 결과에 의미를 준다 — 같은 원격제어 기능이 "완전 접근"과 "백업 접근"에서 각각 얼마나 보이는지가 비침습 취득의 한계선을 정량화한다.

### 4.1 iOS (비탈옥) — 백업 경로가 정공법

1. 암호화 백업 생성(Finder 또는 `idevicebackup2 backup --full`). **암호화를 반드시 켤 것** — 키체인 항목은 암호화 백업에만 포함된다.
2. `Manifest.db` 의 `Files` 테이블에서 앱 도메인 조회:
   ```sql
   SELECT fileID, domain, relativePath FROM Files
   WHERE domain LIKE 'AppDomain%claude%' OR domain LIKE 'AppDomain%openai%'
   ORDER BY relativePath;
   ```
3. 백업에 **포함되는 것**: `Documents/`, `Library/Preferences/*.plist`, `Library/Application Support/`, WebKit 로컬 저장소.
   백업에서 **빠지는 것**: `Library/Caches/`, `tmp/` (iOS 백업 규약상 제외) — 즉 HTTP 캐시·이미지 캐시는 못 본다.
4. **선행 확인**: 앱이 `NSURLIsExcludedFromBackupKey` 로 데이터를 통째로 제외했거나 백업 자체를 막았을 수 있다. 실험 전에 도메인 존재 여부부터 확인하고, 없으면 4.3으로 즉시 전환.
5. **AFC/house_arrest 는 기대하지 말 것** — 비탈옥 iOS 26.5 에서 3uTools·`ifuse` 로 앱 컨테이너를 직접 여는 건 `UIFileSharingEnabled` 를 켠 앱에만 통한다. Claude·ChatGPT 앱은 켰을 가능성이 낮다. 1회 확인만 하고(3uTools `Files` 탭에 해당 앱이 뜨는지) 안 되면 백업 경로로 확정.

### 4.2 Android (SM-A235N, Magisk 루팅) — 내부 저장소 전체 접근

루팅 확보로 제약이 사라졌다. `/data/data/<pkg>` 를 직접 뜬다.

```bash
ADB=/mnt/c/tools/platform-tools/adb.exe
PKG=<대상 패키지>

# 앱 내부 저장소 전체를 tar로 스트리밍 (원본 무변경, 권한·mtime 보존)
$ADB shell "su -c 'tar -cf - -C /data/data $PKG'" > artifacts/remote/android-$PKG.tar

# 개별 확인
$ADB shell "su -c 'ls -laR /data/data/$PKG'"
$ADB shell "su -c 'find /data/data/$PKG -name \"*.db\" -o -name \"*.xml\" -o -name \"*.json\"'"
```

우선 확인 대상:
| 경로 | 내용 |
|---|---|
| `shared_prefs/*.xml` | 계정 식별자·플래그(`hasUsedRemoteControl` 대응물)·설정 |
| `databases/*.db` | Room/SQLite — 대화·세션·원격 지시 이력 |
| `files/`, `cache/`, `no_backup/` | 토큰 저장소·OkHttp 캐시·WebView 데이터 |
| `app_webview/` | 웹뷰 기반이면 여기에 LocalStorage·IndexedDB |

**루팅해도 별도로 챙길 것** (앱 DB가 안 남는 경우의 보험, OS 측 독립 증거라 교차검증 가치가 있음):
| 수단 | 내용 | 명령 |
|---|---|---|
| 실시간 로그 | 세션 중 앱 동작 타임라인 | `$ADB logcat -v threadtime > s3-logcat.txt` |
| 사용 통계 | 앱 포그라운드 진입 시각 | `$ADB shell dumpsys usagestats <pkg>` |
| 네트워크 통계 | 앱별 송수신량 | `$ADB shell dumpsys netstats detail` |
| 화면 녹화 | 지시 문구·시각의 1차 증거 | `$ADB shell screenrecord /sdcard/s3.mp4` |

**루팅 단말의 한계도 같이 적을 것** — 하드웨어 키스토어(TEE/StrongBox)에 든 키는 root로도 못 뽑는다. 토큰이 `AndroidKeyStore` 로 감싸여 있으면 "암호문 blob의 존재·위치·크기"까지가 관측 한계다.

### 4.3 공통 폴백 — 브라우저로 접속한 경우

폰에서 네이티브 앱이 아니라 모바일 브라우저로 접속했다면 난이도가 오히려 낮다.
- iOS: 백업 안의 `HomeDomain/Library/Safari/History.db` (`history_visits.visit_time` = Mac 절대시간, +978307200 → Unix)
- Android: Chrome `History` (SQLite) — 단, 내부 저장소라 비루팅에선 접근 불가 → 대신 Google 계정 활동 기록·화면 녹화로 대체
→ **원격 지시 시각의 타임스탬프 앵커**로 충분하다. 실험 설계 시 "앱으로 할지 브라우저로 할지"를 먼저 고정하고 기록할 것.

### 4.4 시도하지 않는 것

- iOS 탈옥 (iPhone은 비탈옥 전제 유지)
- MITM 프록시로 트래픽 복호화 — 루팅 단말이므로 시스템 CA 주입으로 기술적으로는 가능하나, 실사용자 계정 트래픽 가로채기라 범위 밖. 앱이 certificate pinning을 쓰는지 여부만 `logcat` 에서 확인하고 그친다.

### 4.5 취급 주의

토큰·인증값·세션 식별자는 **존재·위치·형식만** 기록한다. 값 자체는 문서·패널·스크린샷 어디에도 싣지 않는다. 화면 녹화본에 계정 정보가 찍히면 해당 구간을 마스킹한 뒤 보관한다.

## 6. 실패 시 축소안

iOS 백업에서 앱 컨테이너가 안 나오는 것은 **예상된 결과**이므로 실패가 아니라 발견으로 적는다("비침습 취득 한계선" — 루팅 Android 결과와 대조하면 그 한계가 정량화된다). 그 위에, 폰 취득이 시간 안에 아예 안 되면 **로컬 측 규명만으로 정직하게 표기**한다:
"원격제어 연동 구조 규명 + 로컬 측 잔존 아티팩트 실측 완료 / 단말 측 추출은 후속 과제".
§2의 두 아티팩트는 이미 확보돼 있으므로 패널 ②③이 비지는 않는다.
